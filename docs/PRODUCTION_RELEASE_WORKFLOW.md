# SchoolCore — Production Release Workflow

How a change reaches the self-hosted SchoolCore deployment, and how it is rolled
back if it should not have.

This workflow is followed in order. Steps are not reordered for convenience, and
no step is skipped because a change "looks small" — the authorization defect fix
in `db1fe52` touched three authorization handlers and was still not a small
change by this standard.

---

## 1. Branches

| Branch | Role |
|---|---|
| `main` | Integration branch. **Not** the production branch. |
| `selfhost-production` | **The production branch.** Deployed source of truth. |

`selfhost-production` is the accepted production branch and is **not exempt from
CI**. An earlier revision of the CI comment claimed CI did not run on
`selfhost-production`; that was wrong and was corrected, because the branch that
feeds production is precisely the branch that must be verified.

**`main` is not blindly merged.** There is no automatic merge from `main` into
`selfhost-production`, and there should not be one until the deployment is
actually self-hosted in production with Freebuff retired. Promotion is a
deliberate act with a human reviewing the diff, and the diff is expected to be
reviewed against the running system rather than against intent.

---

## 2. The flow

```
development branch
        ↓
  CI (mandatory gate)
        ↓
     review
        ↓
selfhost-production
        ↓
  production backup
        ↓
      deploy
        ↓
  health checks
        ↓
  smoke tests
        ↓
   acceptance
        ↓
  retain, or roll back
```

---

## 3. CI gate

Every commit pushed to `selfhost-production` triggers
`.github/workflows/ci.yml`, and **all five steps must pass**. A red run means the
change does not deploy.

| Step | Command | Requirement |
|---|---|---|
| Install | `bun install --frozen-lockfile` | Lockfile must match `package.json` exactly. A drifting lockfile is a failure, not a warning. |
| Typecheck | `bun run typecheck` | `tsc --noEmit` across the app and the Convex project |
| Tests | `bun run test:unit` | Engine unit tests must pass |
| Lint | `bun run lint` | Zero errors. Warnings are reported and triaged, not suppressed. |
| Build | `bun run build` | Production frontend build must succeed |

Bun is pinned in CI to the version actually validated locally, and
`packageManager` in `package.json` records the same version, so the toolchain is
authoritative rather than implied.

**No step may be weakened to make a change pass.** If a check is wrong, fix the
check in its own reviewed change with the reason recorded, rather than
loosening it inline. There are no placeholder or always-green steps in this
workflow.

The backend authorization regression suite (`bun run test:authz`) is
**deliberately not part of CI** — it requires a live deployment and credentials,
and CI must stay hermetic. It runs against the self-hosted deployment as part of
smoke testing in §7.

## 4. Generated file policy

**`src/convex/_generated/` is committed intentionally.**

| | |
|---|---|
| Location | `src/convex/_generated/` |
| Tracked in git | **Yes** |
| Gitignore | Entry commented out, not deleted, so the intent to commit stays visible |
| Size | ~19.8 KB |
| Deterministic | Derived from `schema.ts`; verified free of secret material |

**Why it is committed.** The directory is generated by the Convex CLI, which is
not run in CI. 168 tracked source files import `@/convex/_generated/api`. When
the directory was gitignored, a fresh clone had no `_generated` directory and
CI failed at typecheck with 4186 errors, every one of them cascading from
`error TS2307: Cannot find module '@/convex/_generated/api'`. Local checks had
been passing only because the directory existed on the developer machine from an
earlier local run — the failure was masked by a stale local artefact.

Committing it makes typecheck reproducible from a clean checkout with no Convex
deployment and no production credentials, which is what a CI gate needs.

**How regeneration is handled.**

- Generated files are **never hand-edited.** A change to a Convex function
  signature or to `schema.ts` requires a real `convex deploy`, which regenerates
  them; the regenerated output is committed alongside the change that caused it.
- On the server the deployment clone is moved to a specific commit by SHA and
  `convex deploy` regenerates the files in place. The working tree is asserted
  clean at the target commit afterwards, so the deployed tree is the tree CI
  verified.
- A pull request that changes `schema.ts` or a Convex signature **without** a
  corresponding `_generated` update is incomplete and should be sent back. A
  `git diff` on `src/convex/_generated/` in a schema-changing commit is a
  useful review signal, not noise to be filtered out.
- Because the files are committed, a schema change that was never deployed
  leaves them stale in the repository. That is the intended trade: the failure
  mode is a visible review signal rather than a CI outage.

## 5. Production backup — required before deployment

**No deployment proceeds without a fresh, verified backup.** This is a hard
gate, not a recommendation.

```bash
sudo /opt/schoolcore/scripts/backup.sh
```

A backup is only acceptable when **all** of the following hold, and the output
must be read to confirm them:

| Requirement | How to confirm |
|---|---|
| Completed without error | `backup <timestamp> COMPLETE` in the output |
| Local copy present | `local : /opt/schoolcore/backups/<timestamp> (size, N files)` |
| Off-site copy uploaded | `offsite : ok snapshot=<id> upload_seconds=N` |
| Retention applied | `retention: applied` |
| Independent health verdict | `sudo /opt/schoolcore/scripts/backup-health.sh` ends `BACKUP HEALTH: HEALTHY` |
| `<id>` is the snapshot this run created | `manifests/restic-snapshot-id.txt` in the new backup directory equals `<id>`, and it is the newest snapshot in the repository |

`backup-health.sh` is deliberately a separate script so backup health is not
graded by the same process that created the backup. Note that it answers a
different question from the off-site freshness check in `production-health.sh`,
and the two did disagree while the latter was defective — see
`MONITORING_AND_ALERTING.md` §7.4. A `HEALTHY` verdict from `backup-health.sh`
does not by itself prove off-site freshness.

During the authorization fix the local snapshot `20260929-201658` (3.1 MB,
8 files, SHA256 manifest written, off-site upload confirmed) was the gate for
deploying `db1fe52`.

## 6. Deploy

The server clone at `/opt/schoolcore/app/source/schoolcore` is a **deployment
artifact** kept on a detached `HEAD`. It is moved to the exact CI-verified
commit by SHA, not by branch name, so the running code is provably the code CI
approved:

```bash
REPO=/opt/schoolcore/app/source/schoolcore
SHA=<full 40-character commit sha of the CI-green commit>

git -C "$REPO" fetch --quiet origin selfhost-production
git -C "$REPO" cat-file -e "${SHA}^{commit}"      # the commit exists
git -C "$REPO" checkout --quiet "$SHA"            # not a branch
[ "$(git -C "$REPO" rev-parse HEAD)" = "$SHA" ] || exit 1
[ -z "$(git -C "$REPO" status --porcelain)" ] || exit 1   # clean tree

AK=$(grep '^CONVEX_SELF_HOSTED_ADMIN_KEY=' /opt/schoolcore/deploy/.env | cut -d= -f2-)
docker run --rm --network schoolcore-net \
  -e CONVEX_SELF_HOSTED_URL="http://backend:3210" \
  -e CONVEX_SELF_HOSTED_ADMIN_KEY="$AK" \
  -v "$REPO:/src" -w /src convex-cli:1.46.0 \
  sh -c "timeout 600 convex deploy 2>&1"
```

The deploy is only complete when the output reports `Schema validation complete`
and confirms no indexes were deleted unexpectedly. A change that drops or
rewrites an index is a schema change and needs its own review and backup.

**Documentation-only commits do not need a deploy.** When a commit changes only
files under `docs/`, the deployed code is unchanged and the deployment already
matches the code. Record the deployed SHA and move on; do not redeploy to
re-assert an unchanged state.

### What each change type requires

| Change | Deploy action |
|---|---|
| `src/convex/**` | `convex deploy` |
| `package.json` / `bun.lock` affecting backend deps | `convex deploy` |
| Frontend only | Rebuild the frontend image and redeploy `schoolcore-frontend` |
| `docs/**` only | None |
| Host scripts under `/opt/schoolcore/scripts` | Not a git deploy; change on the host with a backup and an in-place verification |

## 7. Health checks and smoke tests

Both are required. Passing one is not a substitute for the other.

### 7.1 Health checks

```bash
sudo /opt/schoolcore/scripts/production-health.sh
```

| Check | Expected |
|---|---|
| Frontend, Convex API, OIDC discovery, JWKS | HTTP 200 each |
| Convex dashboard | No public DNS |
| SchoolCore host-published ports | 0 |
| PostgreSQL | Accepting connections |
| Convex backend | Serving, no sqlite fallback |
| Backup health | `HEALTHY` |
| `/srv/platform` | Unchanged and healthy |
| Freebuff | Still paused |

`STATUS=DEGRADED` caused only by a small swap warning, with `vmstat` showing
`si=0 so=0` and ample free RAM, is a strict-threshold artefact and not an
incident — see `MONITORING_AND_ALERTING.md` §3. Confirm with `vmstat` rather
than dismissing it by assumption.

### 7.2 Authorization smoke tests

Authorization is a security control and is re-verified on every backend deploy,
not assumed from a green CI run. The regression suite drives
`convex run --identity`, the same mechanism as the validated harness, and
fabricates no tokens.

```bash
# on the self-hosted host, with the deployment reachable
bun run test:authz
```

The suite covers school admin, teacher, parent, student, anonymous and platform
super admin across `students:get`, `students:list`, `students:stats`,
`students:recent` and the portal queries. Its classification is strict:
validation errors, unrecognised errors and empty responses throw rather than
being scored as a pass or a security denial.

The **full 101-row authorization matrix** is re-run when the change touches
`students`, `staff`, `portal`, `attendance`, `results`, `finance`, `team`,
`accounts` or any enforcer in `session.ts` / `access.ts`:

```
TOTAL PASS=100  FAIL=0  RETEST=0
```

**A final matrix may not contain `INVALID_ARGUMENTS`, `FUNCTION_ERROR` or
`HARNESS_ERROR`.** If one occurs, the test is fixed and re-run; it is never
converted into a pass or a fail. A `FUNCTION_ERROR` is never evidence of
authorization behaviour, and an `INVALID_ARGUMENTS` is never evidence of an
authorization denial.

**Establish the before-state for an authorization fix.** Deploy a fix without
first running its regression suite against the unfixed deployment, and there is
no proof the test would have caught the defect. The sequence that was used for
`db1fe52`, and the one to repeat, is: run the suite pre-fix and record which
rows fail → deploy → run the suite post-fix → re-run the full matrix.

### 7.3 Fixture discipline

Authorization testing uses isolated `P8-`-labelled fixtures created through
application-supported mutations, never direct row inserts. After testing, logins
are disabled rather than hard-deleted where the auth and audit architecture
makes deletion inappropriate, and the following are verified: no orphan
relationships, no broken guardian links, no active test login, and original
records unchanged.

## 8. Acceptance

A change is accepted when, and only when:

- CI is green on `selfhost-production`.
- A verified production backup exists from immediately before the deploy.
- The deploy reports schema validation complete.
- Health checks pass, or any deviation is understood and recorded.
- Smoke tests pass, including the authorization suite when applicable.
- Fixture cleanup is verified.
- The commit on the deployed SHA matches the CI-green commit.

Acceptance is a human decision, recorded — not an inference from elapsed time.

## 9. Rollback

### 9.1 Code rollback

The deployment artifact is a git clone, so a code rollback is a checkout plus a
deploy:

```bash
SHA=<last known-good commit sha>
git -C "$REPO" fetch --quiet origin selfhost-production
git -C "$REPO" checkout --quiet "$SHA"
docker run --rm --network schoolcore-net \
  -e CONVEX_SELF_HOSTED_URL="http://backend:3210" \
  -e CONVEX_SELF_HOSTED_ADMIN_KEY="$AK" \
  -v "$REPO:/src" -w /src convex-cli:1.46.0 \
  sh -c "timeout 600 convex deploy 2>&1"
```

Then re-run §7 in full. A code rollback does **not** undo data written by the
reverted code; if the change wrote data, that data stays and must be assessed
separately.

### 9.2 Data rollback

```bash
sudo /opt/schoolcore/scripts/restore.sh <backup-timestamp>
```

Restoring reverts the database to the snapshot. **Anything written after that
snapshot is lost.** Before restoring, establish what the delta is and confirm it
is acceptable to lose — the restore is not a rollback of the code.

Note that the Convex environment-variable store lives in the database and is
wiped by a restore, so `convex deploy` must be re-run afterwards to repopulate
it, and health checks must confirm the deployment is correctly configured
before users are directed at it.

### 9.3 Choosing between them

| Situation | Action |
|---|---|
| Bad code, no bad data | §9.1 code rollback |
| Bad data, code correct | §9.2 data restore, then deploy |
| Bad code **and** bad data | Restore first, then roll the code back, then re-deploy to repopulate the env store |
| Deployment will not come up | §9.1 first — a code rollback is cheaper and safer than a restore |

### 9.4 The boundary that matters

Freebuff is intact and is the clean rollback target for the **migration itself**
until SchoolCore is accepted. Once users write to the self-hosted deployment,
rollback means losing whatever was written after the snapshot. That asymmetry is
why Freebuff stays paused rather than being retired mid-flight, and why
acceptance is a deliberate act.

---

## 10. Scope

This workflow covers the self-hosted SchoolCore deployment only. It says nothing
about Freebuff, which remains paused, or about `/srv/platform`, which is a
separate deployment that is not touched by any step here.
